# Brief: #145 EVAL-1 Scripted investigation trajectory evaluation suite

Issue: https://github.com/mehaksharma1996/conversational-multi-agent-bi/issues/145
Tier: medium. Check mode: fast (no API or web code changes).

## Outcome
The real investigation graph (proposal, approval service, execution owner, gateway, specialists,
Critic, Supervisor, report verifier) is graded offline under scripted adapters, by expected-versus-
actual comparison, in a reproducible runner with a committed baseline. The churn and retail
investigation cases the graph can genuinely answer become `measured`. Every result says it is
scripted regression evidence, not real-model performance.

## Facts (verified against the code on 2026-11-02)
- `evals/baseline/v2/manifest.json`: top-region and review-category are `requires_agent`;
  October peak is `unsupported`. `evals/investigation/v1/manifest.json`: five churn cases are
  `requires_agent`, and the file is regenerated by `scripts/generate_subscription_churn.py`.
- `packages/evaluation/workflow_cases.py:_entry_problems`: refuses `measured` for investigation
  kinds and for a source case without `scored`. `scored` also drives the live demo report, so
  setting it would count these cases as failures there.
- `src/orchestration/investigation_routing.py`: five of the eight questions are not eligible for
  the investigation route; there is no direct start route in `apps/api`.
- `tests/test_subscription_churn_cases.py` refuses oracle paths anywhere in `apps`, `src`,
  `packages`, so the grader takes reference values as arguments.

## Do
1. `packages/evaluation/investigation_trajectory.py`: content-free observation, expected-versus-
   actual grading per dimension, suite invariants, baseline document, Markdown summary.
2. `tests/e2e/investigation_trajectory_scenarios.py`: scenarios that drive the real graph with the
   existing scripted adapters. `tests/e2e/investigation_trajectory_runner.py`: offline CLI.
3. `evals/investigation/v1/trajectory_cases.json` (expectations) and `trajectory-baseline.json`.
4. Manifests: add `graded_by: investigation_graph` and promote; `workflow_baseline.py` takes those
   grades from the graph, never from the single-query API run.
5. Regression tests: the committed baseline matches; a worse trajectory fails grading and an update
   is refused; grader mutation tests; no content in results.

## Do not touch
`apps/`, `src/`, `packages/investigation`, prompt-bearing modules, `LIVE_ADMISSION_RELEASED`,
`REVIEWED_PROVIDER_EVIDENCE`, `FailClosedAdapters`, the routing default.

## Acceptance
- [ ] The baseline is extended without removing or demoting any case.
- [ ] Results are clearly labelled as scripted regression evidence, not real-model performance.
- [ ] `python -m scripts.check_all` passes; no measured case removed, demoted, or worsened.

## Evaluation and docs impact
`evals/v1` is untouched (no prompt, retrieval, fixture, or safety behaviour changes). Updates
`docs/governance/evaluation.md`, `evals/README.md`, `evals/investigation/v1/README.md`. No ADR.

## Design decisions already made
- `graded_by` on the manifest entry, not `scored` in the source (see Facts).
- Scripted SQL differs from the reference SQL, so equivalence is not a string comparison with itself.
- The routing dimension characterizes the gate as it is, including ineligible questions.
- The runner lives under `tests/e2e/` like the workflow runner, because it needs test fakes.
